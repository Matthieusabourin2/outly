# Outly — Product & Technical Specification (v1)

> Source of truth for the build. Produced from the design interview of 27 September 2026, based on the 7 Outly mockup boards.
> If code and this document disagree, this document wins until it is explicitly amended (see "Amendments" at the end).

Outly is a going-out app for Sydney: discover venues, deals and events, plan the night with your squad, get on the guest list or request a table, check in with a QR pass, pay and split the bill, earn points. It is three products on one backend:

1. **Customer app** (iOS + Android) — boards 1–4
2. **Partner venue app** (iOS + Android, phone or tablet) — board 5
3. **Admin platform** (web, desktop) — boards 6–7

The boards are **mood and intent**, not pixel specs. They were image-generated and contradict each other in details (tab bars, typos, 2025 dates). Where they conflict with this spec, the spec wins.

## 4. Roles and access (D6)

| Role | Surface | Scope |
|---|---|---|
| `customer` (every authenticated user) | customer app | own data; friends; squads they belong to |
| `venue_owner` | partner app | all data of their venue(s) incl. analytics, payouts, Stripe onboarding, staff invites |
| `venue_manager` | partner app | deals, events, bookings, check-ins, payment requests, refunds. No banking/payouts |
| `venue_staff` | partner app | create payment requests, check-ins, today's bookings |
| `venue_door` | partner app | today's guest list + scanner only |
| `outly_admin` | admin | everything, incl. personal user data |
| `outly_marketing` | admin | campaigns, segments (aggregated/pseudonymised user data) |
| `outly_partnerships` | admin | venues, deals, events, memberships |
| `outly_events` | admin | events, promotions |
| `outly_support` | admin | users, reports, bookings, refunds |

One Supabase Auth identity per person. Venue roles live in `venue_memberships` (user × venue × role); Outly roles in `outly_staff`. **Access is enforced by Row Level Security**, never only by hiding UI.

18+ gate: `profiles.date_of_birth` is required; a trigger rejects anyone under 18. Store listings rated 18+ / 17+. ID verification deferred; `id_verified_at` column exists for later.

## 5. Data sources and the Google rules (D4, D5)

**Google Places (live, never stored):** name, address, opening hours, rating, reviews, Google photos, phone, website.
**Stored:** `venues.google_place_id` only (exempt from caching limits). Lat/lng from Google may be cached **≤ 30 days** (`place_cache` table with purge job) — or simply not cached.
**Outly's own data (stored):** categories/vibe tags, Outly-written description, partner status, commissions, Stripe account, deals, events, bookings, check-ins, points, saved venues, squads.
**Partner-provided data** (a partner venue typing its own name, address, photos into the partner app) is the venue's content, not Google's, and may be stored.

Obligations:
- Any screen showing Places content either uses a Google map or shows the Google logo per Google's attribution guidelines.
- Reviews/photos: show author name + avatar + link, and link to `googleMapsUri`.
- Places calls go through `places-proxy` which enforces field masks (request only needed fields — cost is per field tier), per-user rate limits, and in-memory/edge caching **only within the terms**.

Deal honesty rules (D5):
- `public_listing`: the offer is advertised by the venue itself (website/Instagram/menu). Requires `source_url` and `verified_at`. Label in app: "Venue offer · check with venue". Hidden automatically when `verified_at` is older than 30 days (configurable).
- `outly_partner`: created by the venue in the partner app. Label: "Outly deal".
- `demo`: only exists in the demo environment; never in prod (enforced by a check on `is_demo` + environment).
- Booking, guest list, QR pass and Outly Pay: **only** at venues with `partner_status = 'partner'`.

## 6. Data model

The authoritative schema is `supabase/migrations/0001_init.sql`. Summary:

**Identity:** `profiles` (1:1 with `auth.users`: username, display name, avatar, date_of_birth, referral_code, preferences jsonb, alcohol_promos_opt_in, friend_activity_visibility, no_show_count, tier), `outly_staff`, `venue_memberships`, `push_tokens`.
**Venues:** `venues` (google_place_id, partner_status, categories, vibe_tags, description, commission_rate, booking_commission, stripe_account_id, booking settings, is_demo), `place_cache` (≤30 d lat/lng), `saved_venues`.
**Offers:** `deals`, `events` (both with `source`, `source_url`, `verified_at`, status, schedule).
**Bookings:** `guest_lists` (venue × night, capacity), `bookings` (type guest_list/table_request/instant, status, party size, QR nonce, check-in, decision, expiry).
**Social:** `friendships`, `blocks`, `squads`, `squad_members`, `squad_candidates`, `squad_votes`, `messages`, `reports`, `activity_posts`, `activity_audience`.
**Money:** `payment_requests`, `payment_shares`, `points_ledger`, `vouchers`, `stripe_events`.
**Engagement:** `notifications`, `campaigns` (draft → approved → sent; send requires a second human), `ai_conversations`, `ai_messages`.
**Ops:** `audit_log`.

Key server-side functions (SECURITY DEFINER, checked):
- `join_guest_list(guest_list_id, party_size)` — locks the row, enforces capacity, partner-only.
- `request_table(venue_id, starts_at, party_size, note)` — partner-only; sets `expires_at = now() + ttl`.
- `decide_booking(booking_id, accept)` — venue_manager+.
- `check_in(booking_id, nonce)` — door+; single-use nonce; called by `qr-check-in` Edge Function after HMAC verification.
- `expire_and_no_show()` — cron every 5 min.

## 8. Partner app (board 5)

Tabs: **Today · Scan · Bookings · Promote · More**, filtered by role (door sees Today + Scan only).

- **Login / venue switcher** (a user can belong to several venues).
- **Today:** tonight's guest list with counts, pending table requests (accept/decline with countdown), key numbers.
- **Scan:** camera QR → server validation → green/red result with name and party size.
- **Bookings:** upcoming / checked-in / past; no-shows.
- **Promote:** create/edit deals and events (draft → scheduled → active), toggle "Show on Outly".
- **Payment request:** amount + table → one-time QR shown on staff device.
- **More:** analytics (bookings, check-ins, revenue via Outly, top nights), payouts (Stripe status, read-only), staff & roles, venue profile, Partner AI.
- **Cut:** Live Orders.

## 9. Admin platform (boards 6–7)

Sidebar: Dashboard · Venues · Deals & Promotions · Events · Bookings · Users · CRM · Payouts & Transactions · Reports & Exports · AI Copilot · Settings & Permissions.

- Dashboard: totals, trends, live now — computed from real tables (materialised views where needed).
- Venues: list, partner status pipeline (listed → pending → partner → inactive), memberships, commission settings, Stripe onboarding status.
- Deals/Events: moderation queue, verification of `public_listing` items (source URL, verified date).
- Users: search, profile, bookings, reports, block/suspend.
- CRM: segments, campaigns (draft → approve by a second staff member → schedule/send), results.
- Transactions/Payouts: from Stripe test data + our tables.
- Reports: CSV exports (users, bookings, revenue) — role-gated.
- Settings: staff members and roles, audit log.

## 10. AI (D10)

| Surface | Model | Reads | May do | Never alone |
|---|---|---|---|---|
| Customer "Outly AI" | Claude Haiku 4.5 | Places (proxy), deals, events, user prefs, saved venues | Suggest, build a plan, prepare booking request / squad vote | Book, pay, message |
| Partner AI | Claude Sonnet 5 | Own venue data only (RLS) | Analyse, suggest, draft promotion/event | Publish |
| Admin Copilot | Claude Sonnet 5 | Aggregates; personal data only for `outly_admin` | Analyse, segment, draft campaigns/emails | Send, modify venues |

Rules: tools return real IDs; the model may only recommend venues/deals returned by tools. Every write goes through a confirmation screen describing exactly what happens. Responsible-service rules in system prompt: no "cheapest way to get drunk" framing, no drink suggestions after 01:00 local or after 3 check-ins the same night, offer food/water/transport, respect `alcohol_promos_opt_in = false`. Limits: ~30 customer messages/day, cost cap per user/day, logged in `ai_messages` (included in data export).

## 13. Non-negotiables (checklist for every PR)

1. RLS on every table; a new table without policies is a bug.
2. No secret (Google, Stripe, Anthropic, service role) in any client bundle.
3. Only `place_id` stored from Google; Google map wherever Places data is on a map; attribution present.
4. No deal or event shown without `source`; `public_listing` requires `source_url` + fresh `verified_at`.
5. Booking/guest list/pay only at `partner` venues.
6. Under-18 cannot create a profile.
7. AI never performs a write without explicit user confirmation.
8. Users can report and block; blocked users cannot message or see each other's activity.
9. Stripe in test mode in v1 — live keys must not exist in any environment.
10. Money stored as integer cents (AUD).
